## 3. 推进次序与治理覆盖

1. **最小启动轮**：核实清单、漫画身份、状态源、当前写者及主分支交付条件；先修妨碍本任务启动的规则冲突。提出一版最小统一接入契约，复用现有实现；不要等全局完美再处理漫画。
2. **漫画优先轮**：按第 4 节定位、修复、回归并完成实际受影响项的可验证恢复，再交付该仓库主分支。需要的全局修复另开串行单元，避免混合候选。
3. **逐项目轮**：逐个完成下表检查、必要修复、统一模板接入和主分支交付。全局共因在全局范围修一次；项目保留必要差异。一个项目未闭环不把它移出覆盖分母。
4. **Hub 收口轮**：验证全部项目接入与刷新、来源可追溯及飞书本地预览；由一个新的只读 Agent 仅从 Hub 入口完成交接读取，核对所有交付收据。

| 检查面 | 必须回答的问题与修复目标 |
| --- | --- |
| Agent 入口与覆盖 | Codex 实际加载哪层规则？重复、相互矛盾、过期路径和无效路由在哪里？个人角色/Skills 的职责、工具能力与实际可用性是否一致？ |
| 轮次与状态 | 谁是唯一状态写者？completed、accepted、delivered 是否分开？能否正确暂停、恢复、失败重试、复审退回，是否出现终态误判或旧快照覆盖新结果？ |
| 审核与恢复 | 审核是否绑定同一语义候选？是否因记录时间、PASS 元数据或自包含哈希反复重审？失败项能否带明确原因和版本进入合法修复路径？ |
| 仓库流程 | 启动/测试/构建命令是否仍可运行？依赖和 CI 是否匹配？主分支、远端、分支保护、未交付改动与真实阻塞是什么？不得靠跳过测试通过 |
| Hub 接入 | ID、真实路径、状态来源和映射是否有效？读取失败、无源、过期和权限限制是否可见？业务进度是否被存储完成或 README 描述冒充？ |

按问题风险选 DIRECT / REVIEWED / GOVERNED。普通局部可恢复修复直接完成；广泛行为变化用独立 Judge；全局/项目控制面变更由 Governor 冻结合约、Root 写入并登记候选、fresh Judge 只读审查、Governor 决策。按适用项目的明确审查要求执行，不把三角色强加给每个简单文件修改。

先删重复、合并、复用或缩小范围，再考虑新机制。不新增通用调度器、锁服务、第二套 Goal、常驻审计循环或重复进度账本。相同语义候选仅审一次；实现变化才重审，审查/交付元数据不放进候选自包含哈希。不能用减少流程为由降低业务质量标准。

## 5. 所有项目统一接入模板

**统一的是模板、字段语义与读取结果，不强迫重命名所有项目的状态文件。** 先复用 Hub 现有 registry、`data/design_governance/connection_adapters.json` 及 `src/hub/connection_sources.py`、`connection_records.py`、`connection_refresh.py`、`project_service.py`。当前使用的 source-plan/authority-bundle 版本由代码入口核实，不把准备时 v4 写死为永久权威。

交付一份带 schema_version 的共享模板/Schema、填写说明和校验入口；每个项目落地同格式的轻量接入声明，优先复用已有文件位置。声明只写稳定身份、状态源指针、解析映射与验证入口；动态业务字段从唯一状态源派生。无状态源时在项目内建立一份最小权威状态，并使其正常工作流负责更新；不能靠 Hub 每次猜摘要。

以下是最少契约，最终字段名与现有 Schema 对齐后冻结，不另造平行协议：

| 组 | 必须表达的字段/语义 |
| --- | --- |
| 身份与来源 | schema_version、稳定 project_id、名称、状态源相对路径及格式、适配器/映射；本机绝对根路径由 registry 管理 |
| 当前工作 | 目标、当前阶段/轮次、状态、completed 与 accepted、下一步行动及负责角色；没有依据时明确 unknown |
| 进度 | 可核实的完成项/总项及计数口径，或里程碑列表；没有合法分母时不造百分比 |
| 阻塞与恢复 | 阻塞原因、受影响项、恢复条件、可用重试/重做入口、是否等待用户；不暴露秘密和原始私密内容 |
| 验证与交付 | 验证命令/结果引用、accepted 依据、目标远端/主分支及交付收据引用；本地完成与远端已交付分开 |
| 新鲜度 | 源修改时间/版本/指纹、读取时间、read_status、stale 及错误原因；投影不能比来源更“已完成” |

Hub 对全部登记项使用同一输出格式，包括离线/缺失/无权限/无源项目。证明每个字段能追溯到来源；解析报错不能变成空的成功，过期快照不能静默当作最新。保留既有合法读取边界，真实根解析不能越界。

关键验收：修改项目唯一状态源后，经正常刷新即可在 Hub 看到一致变化；重复刷新不重复产生业务项；重启可恢复；来源指纹变化触发正确失效/重绑；离线/损坏/权限拒绝显示明确原因。新 Agent 从 Hub 文档和统一输出完成全部项目状态读取，不必逐个浏览业务仓库或依赖聊天记忆；仅需要诊断时才按路由深入。

## 7. 每轮 GitHub 主分支交付

这是执行阶段的强制闭环，属于本次所有者明确授权；**不能沿用旧的仅当前跟踪分支策略**。

1. 首次处理每仓库时核对仓库身份、远端与真实主分支（main/master 或仓库实际默认分支）、上游及保护规则。不能从 Hub 当前 `agent/...` 分支推断主分支，也不改远端或绕过保护。
2. 保护并盘点原有 dirty 工作，按所有者补充授权将其纳入逐仓库交付清单；先冻结当前交付单元的精确 diff，再只提交已经检查和验证的内容。其他既有内容保留待交付状态，不混入当前候选。若工作分支含不同任务历史，使用从已核实主分支建立的隔离工作树迁入明确候选和必要依赖；不能未经检查把整条旧分支合入主分支。当前已冻结的单元继续按其边界完成，原有未提交内容在后续单独核对、验证和交付。
3. Root 复现相关检查并完成适用审查，然后按仓库允许方式提交、正常合入并推送主分支；受保护分支走正式 PR 与检查流程。自行解决任务内可恢复冲突，禁止强推、绕过检查或改写历史。需要第三方审核/缺少权限时保留具体待交付项，不把 PR 创建视为已到主分支。
4. 子项目改动交付到**该子项目仓库主分支**；Hub 改动交付到 **Hub 主分支**。涉及两者时先子项目后 Hub，串行验证和提交，各自形成清晰交付单元；不能只推 Hub 日志替代子项目代码交付。
5. 全局 Codex 规则/角色/个人 Skills 的任务改动，优先复用既有受版本管理的来源；若缺少来源，在 Hub 治理目录保存本任务涉及的可恢复、非秘密源文件及目标路径映射，形成明确授权的版本管理来源，推送 Hub 主分支。随后在独立全局控制单元安装/核对实际生效文件及哈希。两边一致才算完成；不能仅提交摘要声称配置已同步，不能打包整个 `~/.codex`、运行数据库或秘密配置。
6. 检查 fetch/ls-remote 或服务端结果：本轮提交确实位于远端主分支历史中；记录仓库、主分支、候选提交和观察到的远端 SHA，核对适用 CI。若主分支后续前进，以祖先包含关系确认，不要求分支永远停在自己的提交。收据置于原生输出/Hub 管理记录，不制造“提交包含自身 SHA”的循环。
7. 无改动的检查轮记录 no_change 和验证依据，不造空提交。无 Git/无远端项目仍需治理和可读状态，但标明交付缺口；不擅自创建远端仓库、借用兄弟仓库或宣称 GitHub 已同步。若需新仓库，待所有者明确目标。
8. push 失败或结果不明先核实远端，避免重复提交。affected 单元保留 pending_delivery，不宣布该轮交付完成；继续独立只读发现和不依赖该交付的工作，不积累该仓库下一轮写入来掩盖未交付。每轮回复列出已验证主分支链接/提交及未交付项。

全局变更还须区分 written、discovery-verified、behavior-verified；需要新进程加载时明确记录，不假定现有会话热更新。

## 8. 验证、结束与恢复

项目修复运行最接近缺陷的有效检查及项目必需检查；Hub 控制面轮按路由执行仓库检查、状态一致性和相关测试。可复用入口：

```text
python3 scripts/check_repo.py --task-id ALL-PROJECTS-CODEX-GOVERNANCE-V1
python3 scripts/round_consistency_check.py --json --task-id ALL-PROJECTS-CODEX-GOVERNANCE-V1
python3 scripts/check_registry.py
python3 scripts/hub_connections.py schema
python3 scripts/hub_refresh.py validate
```

Hub 相关测试集中于 `tests/test_hub_sources.py`、`tests/test_hub_connections.py`、`tests/test_hub_refresh.py`、`tests/test_hub_project_service.py`；按仓库实际测试运行器执行。刷新会写本地记录，实际执行前核对当前 CLI 及授权，不把 schema/validate 成功等同实际刷新成功。

全部完成必须同时满足：

- 全量项目均有经证据核实的治理结论、统一接入声明和可读业务状态；没有静默遗漏、假进度或悬空指针。
- 漫画真实卡点有可复现根因，修复通过回归，受影响项达到第 4 节要求；其他已发现的同类可修复问题完成闭环。
- Codex 规则、代码、测试、状态与 Git 交付行为一致；所有实际变更按第 7 节交付，必要生效验证完成。
- Hub 全量读取/刷新与错误显示验证通过，飞书本地准备可演示，新的只读 Agent 从 Hub 入口完成独立交接读取。

只有全部条件满足才结束为完成。blocked、unknown、pending_delivery、付费生成待执行或缺少状态源均须明确保留；经所有者缩小范围才能改验收分母，不能自行将障碍改成“例外通过”。

持续在同一原生 Goal 增量推进。用唯一管理状态保留本轮证据、失败指纹、累计预算（仅真实遥测）、未完成项和一个下一步；业务细节留在项目状态源。收到停止/暂停立即停止本任务新效果并按原生身份处理本任务子 Agent；不伪造暂停 API，不把未完成任务标成 complete，也不创建自动化替代 Goal。
