计划 ID：`FEISHU-PROJECT-CLOUD-SYNC-V1`。版本：1，2026-09-14。

读者：所有者、接手实施的 Agent、以后维护同步程序的人。用途：把已存在的项目数据链接到真实飞书云端，并验收无人值守运行。范围、接口约束或验收变化时更新本文；当前进展、人工准备结果、阻塞、轮次和唯一下一步只写 `STATE.yaml#feishu_cloud_sync`。本文是实施规格，不是第二本进度账。

## 1. 先完成需要所有者参与的准备

尽量在第一个实施轮集中完成 H01–H07 的人工配置动作。Agent 先准备具体接口权限清单、配置模板和安全录入工具，再让所有者执行只能本人完成的动作；不能要求先交一包密钥再开始调查。每项记录 `not_checked / waiting_owner / configured / ready / blocked`、非秘密定位信息和脱敏检查结果。`configured` 表示配置与授权已就绪，`ready` 表示实际验证通过，不能把两者混同。

### 1.2 权限核对不能遗漏的两层

| 能力 | 实施时匹配的接口族 | 应用后台权限 | 目标资源权限 |

后台 scope 名称、接口限额和产品套餐应在 P00 使用当时官方页面与实际租户核对并保存具体标识；不能把上表中文能力直接当 API scope 字符串。优先应用身份 `tenant_access_token`，适合无用户交互的程序运行；只有实测应用身份无法覆盖本人目标资源时才评估用户 OAuth，提前核对 refresh token、撤销与再次授权路径，不能每天手工粘贴短期 token。

已核对的接口基线如下。Sheets 文档位于 v3 目录，不代表所有数据接口 URL 都是 v3；不要推测端点版本。创建工作表/字段、读取、Base 创建等其余端点在 P00 补入实际权限矩阵。

| 操作 | HTTP 接口（域名 `https://open.feishu.cn`） | 官方页面限制 / 实施要求 |
|---|---|---|
| 创建独立 Sheets | `POST /open-apis/sheets/v3/spreadsheets` | 指定 folder_token；创建不带内容；页面频率为 20 次/分钟，批量创建须节流 |
| Sheets 批量范围写入 | `POST /open-apis/sheets/v2/spreadsheets/:spreadsheetToken/values_batch_update` | 单次至多 5000 行、100 列，单元格至多 50000 字符，官方推荐不超过 40000；写入会覆盖指定范围，只能写自有区域 |

### 1.3 一次性准入演练

人工准备与程序探针交替完成：P00 确认 H01/H02 与 H03–H07 配置/授权就绪 → P01 有界准入后进行 token/资源探针 → P03 **一个真实项目**的最小 Sheets 与 Base 创建、字段写入、完整回读 → 所有者打开验证可见性 → P07 在调度身份下复测。第一次云探针的前置是身份、目标、字段、凭据和该探针授权明确，不是所有 H 项已完成云实测。H03/H04 的 `ready` 由 P03 产生，H07 的 `ready` 由 P07 产生；不能循环等待。云端演练使用真实来源的最小批准字段；合成数据只进入隔离本地测试，不能混入正式云数据。

覆盖“新增项目是否还需人工逐文件授权”的实测：同一目录再由 API 创建一份属于本任务的真实项目文件，确认应用与所有者均可访问。若不能继承，就在 P00/P01 解决目录/资源权限方案，不能等全量接入时再发现 24 次人工操作。

H01–H07 未实测通过前，真实云链路保持未验收；本地客户端、投影和测试仍可独立推进。外部审批、登录、付费或所有者才能决定的边界不能由 Agent 假称“当场解决”。Agent 必须立即定位最小人工动作，并在同一 STATE 留下恢复条件，不把整条路线长期悬置。

## 4. 目标数据链与云端结构

```text
项目真实业务源 / 已登记状态
  → 项目普通 Python 导出器 → .hub/status.json
  → Hub 原有 sync / import → 同一个 SQLite 账本
  → 校验并冻结发布快照与字段白名单
  → 项目独立 Sheets 文件
  → 总 Bitable 的项目目录、指标、问题及同步状态
  → 两端 API 回读比对 → 记录成功版本
```

Sheets 与总 Base 消费**同一份程序投影**。Base 不通过 Agent 读 Sheets 求和，也不依赖跨文档公式或平台原生数据同步功能；发布过程可以先写 Sheets，再写 Base 并各自回读。两个远端资源没有分布式事务，必须显示部分成功，待两端同版本核对后才标项目整体成功。

### 4.1 每项目独立 Sheets 文件

固定资源绑定以 `project_id` 为键：工作簿 token、实际 URL、各工作表 ID、目标目录、schema 版本、管理范围、最后确认版本。默认标题「项目名｜项目数据」，标题变化不能创建新文件。

建议工作表：`项目概况`（真实管理字段、更新时间、版本、质量）、`指标明细`（每个合法指标一行）、`问题与缺口`（当前 issue）、`同步信息`（两端版本、最后成功/失败与错误类别）。业务记录级明细仅在项目已有明确可发布结构时增加，以源 ID 保持身份；不能把全文/二进制附件上传设为前置。

所有写入限定程序拥有的工作表/列/行；预留人工备注区，不能全文件覆盖。文本 ID 保留前导零，文本中的 `=` 等不得误解释为公式。日期、时区、空值、长文本及数值精度有明确序列化和回读规则。

### 4.2 一个总 Bitable

同一 Base 至少有以下普通可写数据表；用 project_id 关联，字段显示名可以中文，但程序使用稳定字段映射。

| 数据表 | 粒度 / 主键 | 必须可见的数据 |
|---|---|---|
| 项目目录 | 每登记项目一行，`project_id` | 名称、项目文件链接、目标/阶段/状态、源质量、现存/延后/移除处置、最后源观察时间、两端发布版本与最近尝试 |
| 项目指标 | `project_id + metric_id + unit + canonical(dimensions) + counting_basis` 的稳定键 | 值、单位、维度、窗口、口径、来源版本、质量、原因、snapshot_id；需要聚合时使用现有定义 |
| 问题与缺口 | 项目 + 稳定 issue 身份 | 源缺失、校验失败、依赖/业务阻塞和发生/观察时间，未知时间保持 null |
| 同步状态 | 每项目每目标一个当前状态，运行明细留本地 | last_success、latest_attempt、数据时间、发布确认时间、两端差异、恢复条件；不能用最近心跳代替数据新鲜度 |

提供“全部现存项目”“同步异常/过期”“有业务阻塞”等基础筛选视图和项目链接；本任务不另建 Hub 图表或网页。总表不是只有项目名和链接，必须能在其中查询全部已批准指标与缺口，必要的通用总计按相同单位、窗口、口径分别聚合。

字段复用 `project_id / metric_id / value / unit / dimensions / observed_at / business_at / source_ref / source_version / quality / reason / counting_basis` 及现有 metric definitions。`unknown != 0`，`stale != fresh`，`business completed != governance completed`；比例保留分子分母，不能平均百分位，不把净变化当吞吐。成本仅来自真实遥测。来源引用应转成批准的相对引用/opaque ID，完整本机路径、账户信息、带密钥 URL 和原始 source_record 不默认上云。

### 4.3 增量、幂等与恢复

- 在原 Hub SQLite 扩展必要的目标绑定与云发布记录，不另建重复采集器、Agent 调度系统或第二个开发进度账。凭据不进 SQLite；运行元数据与 STATE 的开发进度职责分开。
- 发布身份至少绑定项目、源 snapshot_id、投影/schema 版本和目标 ID。记录 payload hash、目标记录 ID、开始/结束、重试类别和回读结果。同一数据无变化时不增行、不重建表、不增加无意义历史版本。
- 云 API 没有统一 upsert 保证，应用按稳定键查询/更新/创建。创建或批量写响应丢失先读取确认，不盲目重发。进程重启或本地映射丢失可以从目标范围和稳定键重建绑定；只匹配本任务资源。
- 同一目标表写入串行；原有项目并发规则不被云写入放大。处理 HTTP 错误和 HTTP 200 下的非零业务码，分页穷尽、合理批量、限流退避与抖动、超时、短期网络故障、token 刷新、部分失败；重试有上限，永久权限/类型错误不循环。
- 本地读快照按固定版本完成全部分页；源版本在分页中变化时重新取一致版本。长分页、记录数量/正文长度上限在 P00/P02 以实际文档和租户测定，不能静默截断指标。
- 源移除/权限撤销停止新读取；旧行标历史/不再适用。源指标消失要标 inactive，不永久保留为当前有效数。默认不删除用户数据，不以清空表重传实现同步。
- 失败后保留历史成功值和原始数据时间，同时明确失败/过期。旧快照不能靠重发伪造 fresh；一端成功另一端失败必须可见，可恢复未完成目标且不重跑已确认步骤。
- 全局、单项目与单目标可暂停，暂停保留绑定和数据。运行配置/投影 schema 版本变更须可迁移；回退仅停发布或恢复任务拥有的明确配置，不回滚项目原始业务数据。

## 5. 分阶段执行路线

每阶段可拆成多个可验证、可交付的执行轮；不强求“一轮一阶段”，不为轮次制造文档。预计 12–20 个有效实施轮，置信度低至中：取决于 H01–H07 和实际 24 项源状态。每轮根据已通过验收更新剩余估计；无硬性 token 预算，不重置既有累计事实。

| 阶段 | 工作与依赖 | 本阶段验收 / 完成证据 |
|---|---|---|
| P00 现状与人工准入 | 最新 main、唯一 STATE、来源映射、既有目标核对；冻结范围和字段；给出 H01–H07 具体资料；准备 doctor 和安全录入入口；有界核对官方接口 | 每个 required 项有来源处置；所有者待办一次列齐；身份、目标、字段及应用配置/授权具体明确，机器可做脱敏检查。云实测项保持 configured/待测，不要求在 P00 已完成 P03/P07 |
| P01 云访问准入及最小客户端 | P00 确认目标；对真实云外部效果与控制面修改走适用 GOVERNED 路由，Root 写准入策略/gate、只读 Governor/新 Judge；保持旧通知和源项目禁写边界 | 有界修订两份 policy、gate、新任务 scope/状态选择器、runner 候选路径选择及一致性检查和兼容测试；只放行指定投影/资源及最小探针。client/credential provider 无敏感日志；token 刷新与错误码测试通过 |
| P02 发布投影与本地契约 | 可与人工准备独立推进；复用 v3 快照、定义和现有账本 | Sheets/Base 投影、稳定键、完整分页、白名单、类型/空值、来源版本绑定、跨页一致性均有测试；dry-run 只显示真实可发布计划，不造云成功 |
| P03 一个真实项目闭环 | P00 配置/授权就绪、P01 有界放行 + P02；按“源健康、低敏感、真实指标”选试点，例如符合条件的 light-novel，不能硬选不可用项目 | API 创建独立 Sheets 和总 Base；真实源→Hub→Sheets→Base 全字段/行键回读匹配，完成 H03/H04 实测。相同输入重跑无重复。所有者可打开两个结果；成功 URL 与摘要证据可交付 |
| P04 增量与故障恢复 | P03；云发布记录扩展；先用本地故障注入验证，再在任务拥有目标做安全实测 | 源真实变化传播、响应丢失/中断恢复、单端失败、分页、限流、token 失效、字段变化和旧值过期处理通过；不改真实业务值制造成功。等不到自然变化时保留待验证，不以 fixture 替代真实变化验收 |
| P05 全部已登记项目覆盖 | P04；逐项目或小批迁移，先读当前单元。云端写入串行；如必须修导出器，进入对应仓库后串行修改/验证/交付 | 每个 required 项有独立工作簿和总表目录项，批准指标/问题完整且回读一致；空项目/阻塞项目真实标明。受保护 WIP、removed_local 和排除项不碰；两新项目按第 3 节处理 |
| P06 总多维表可用性与完整对账 | P05，各项目独立证据复用 | 目录唯一、每项目可点开；全部指标和问题可查，三类基础视图正确；跨项目聚合无混单位/窗口/重复计数；两端版本、来源质量和遗漏数量可见 |
| P07 独立程序定时运行 | P03 后即可早测，最终以全量 P05/P06 验收；完成 H05/H07 | 提供普通 Python 运行命令与用户级 launchd 配置/安装卸载说明；不调用模型、Agent、MCP 或 Codex automation；关闭这些客户端仍能由调度器运行 |
| P08 运行观察与交接 | P04–P07 完成；真实调度连续观察 | 至少 24 小时观察窗内有至少 3 次自动成功、一次真实源版本变化传播、token 自动更新/刷新、一次进程重启恢复；盘离线/网络故障可控验证后恢复。机器离线时间明确记录，不能冒充连续服务 |

P00 的安全录入工具、P02 本地投影等普通实现用 DIRECT；覆盖面较广且判断困难的同步行为用 REVIEWED；P01 准入与实际云外部效果按真实风险 GOVERNED。独立审查只服务真实边界，不每个普通文档轮都套三角色流程。保持 root 的同仓写入、证据登记、Git 和外部效果职责。

现有 `scripts/governance_scope.py`、`scripts/auto_advance_runner.py` 的上下文/候选选择和 `scripts/round_consistency_check.py` 仍以旧任务状态为入口。P01 必须把新任务 ID 路由到 `STATE.feishu_cloud_sync` 及本轮真实候选，同时保留旧 v3 行为；覆盖新旧 scope、候选遗漏和拒绝越界的测试。适用文件以实现时调用关系为准。切换前旧 task-id 的检查只证明旧兼容基线，本次规划另外直接验证新 STATE/候选，不能把旧 gate 通过当作新云候选获准。

## 7. 程序入口与验证设计

在现有 `hub.py` 中扩展命名清楚的飞书入口优于另起一套系统。以下是**待实现的命令契约**，本次尚不存在：`feishu doctor`（脱敏预检）、`feishu plan`（真实快照 dry-run）、`feishu provision`（幂等资源创建）、`feishu publish`（指定快照/项目发布）、`feishu reconcile`（两端完整回读）、`feishu status`、`feishu run-once`（一次采集/发布）。准确语法由实施单元与 `--help` 一起交付，不让新 Agent 误把本节示意命令当现成工具。

| 429、写冲突、临时服务错误 | 单表串行、限额内分批、退避；不确定写先回读；相同版本同方法两次无进展就诊断/改方法，不靠无限重试推进 |

| main 推送被拒 | fetch 并核对新增提交，保留他人变更，基于最新 main 整合任务自有单元并重验；保护规则要求人工时只暂停远端交付，保存已验证本地提交 |

同一 `STATE.feishu_cloud_sync` 保存：task ID、计划版本、stage/unit/project、frozen scope 引用、H01–H07 结果、A01–A09 证据、候选路径/版本、失败指纹、最近交付、去重执行轮数、下一步。按闭合键去重，重试/状态查询/子 Agent 回调不另计轮；旧 v3 65 轮保留为历史，不冒充本目标新轮次。轮末按已安装 goal-progress 技能做简短核算；task-health 仅在实际触发时使用。

每轮完成一个真实可审阅单元后：实现 → 相关检查 → 精确 diff 复核 → 更新 STATE → 仅 stage 任务拥有文件 → commit → 正常 push 到对应仓库 main → 核对远端 SHA 与适用 CI。主分支在别的 worktree 打开时可从最新 origin/main 建独立同仓分支，再正常 `git push origin HEAD:main`；不切换/重置别人 checkout，不强推。无变化不造空提交，后续启动前核对 main 是否包含该已交付单元。

提交自身无法在同一提交中填写自己的 SHA：STATE 保存已知前序交付和本轮 pending/待远端核对事实，push 后由 Git/远端作为此次交付证据，下一次状态更新登记已验证 SHA；不制造递归“写收据→再提交”。最终交付在回复给出准确远端提交。
